# BasketWise — Data dictionary

## Demo dataset: `Data/synthetic_retail_transactions.csv`

The data is synthetic, generated by `scripts/generate_data.py` with seed 42. Every value was produced by the generator. None of it is real customer, price or sales data.

| Column | Type | Example | Description |
|---|---|---|---|
| `transaction_id` | text | `SYN-T000001` | Synthetic transaction (basket) ID, numbered in date order |
| `transaction_date` | date (ISO) | `2025-01-01` | Synthetic date between 2025-01-01 and 2025-06-30; weekends are weighted 1.4× |
| `customer_id` | text | `SYN-C00732` | Synthetic customer ID; some customers shop much more often than others |
| `product_id` | text | `P006` | Product code from the generator's catalogue |
| `product_name` | text | `Paneer` | One of 47 products |
| `category` | text | `Dairy & Eggs` | One of 8 categories |
| `quantity` | integer | `1` | Units bought (1: 78 %, 2: 17 %, 3: 5 %) |
| `unit_price` | number | `90.0` | Fixed synthetic price per product, in INR |

**Size with the default settings:**
- 29,763 rows across 8,000 transactions, 47 products and 8 categories.
- 1,368 synthetic customers appear (up to 77 transactions each; median 4).
- The average basket holds 3.72 products (median 4, largest 13), and 12.3 % of transactions contain a single product.

**Categories:**
- Dairy & Eggs
- Bakery
- Beverages
- Snacks
- Fruits & Vegetables
- Staples & Cooking
- Household
- Personal Care

### How baskets are generated

Each synthetic customer has two favourite shopping missions and one to three habitual products. Each basket is built as follows:
1. The basket contains 0, 1 or 2 missions (probabilities 30 %, 55 % and 15 %). For each mission, 70 % of the time it is one of the customer's two favourites.
2. A mission always adds its core product, and adds each companion product with a fixed probability. For example, "pasta night" always adds Pasta, and adds Pasta Sauce 60 % of the time and Cheese 40 % of the time.
3. Each habitual product is added with a 25 % chance.
4. Independent purchases are drawn from overall product popularity (Poisson-distributed counts), so baskets also contain unrelated items.
5. Baskets are capped at 15 products.

There are 12 missions:
- breakfast
- tea time
- coffee break
- pasta night
- home cooking
- baking
- party snacks
- laundry
- bath care
- oral care
- fruit run
- paneer curry

The planted associations are known ground truth for testing. They are also stronger than typical real retail associations.

**How generated data is recognised.** Every transaction ID (`SYN-T000001`) and customer ID (`SYN-C00001`) follows the generator's format. When a file in which *all* transaction and customer IDs follow it is loaded, from any path or as an upload, BasketWise labels it synthetic, and reports keep the synthetic-data disclaimer. Files without a customer column, or with any other ID, are never labelled synthetic.

Run `python scripts/generate_data.py --transactions N --products P --seed S` to create other variants. P is between 8 and 47; smaller catalogues keep every category represented.

## Demo upload with known problems: `Data/demo_upload_with_issues.csv`

This file has the same columns as the demo dataset plus a `store_id` column. It was generated with:

```
python scripts/generate_data.py --transactions 3000 --seed 7 --with-issues --output Data/demo_upload_with_issues.csv
```

Each problem was injected into its own random set of rows, so the validator should report exactly these counts (this is tested):

| Injected problem | Rows | Reported by validation as |
|---|---|---|
| Blank product names | 110 | Removed: blank product names |
| Missing transaction IDs | 55 | Rejected: missing transaction ID |
| Upper-case variants (`MILK`) | 219 | Merged: capitalisation variants |
| Names wrapped in extra spaces | 219 | Fixed: extra spaces |
| Duplicated rows | 110 | Removed: duplicate product in a transaction |
| Extra column `store_id` | 1 | Ignored columns |

Three transactions lose all of their products to blanking, so 2,997 of the 3,000 transactions remain valid.

## Accepted upload formats

Files with the extension `.csv`, `.txt` or `.tsv` are accepted. Comma, semicolon, tab and pipe separators are detected from the header row. Text is read as UTF-8 (with or without a byte-order mark), as UTF-16 when it starts with a UTF-16 byte-order mark, and otherwise as Windows-1252, with Latin-1 as the last resort; a warning names any encoding other than UTF-8. Trailing empty columns without a header (common in spreadsheet exports) are dropped.

Column names are matched after normalising them: case does not matter, CamelCase is split (`InvoiceNo` → `invoice_no`, `CustomerID` → `customer_id`), and spaces and symbols are treated as underscores. If two columns normalise to the same name, the first is used and the other is listed as ignored.

| Role | Accepted column names |
|---|---|
| Transaction ID (required in long format) | `transaction_id`, `transaction`, `transaction_no`, `invoice`, `invoice_no`, `invoice_id`, `invoice_number`, `order_id`, `order`, `basket_id`, `receipt_id`, `bill_no` |
| Product (required in long format) | `product_name`, `product`, `item_name`, `item`, `product_description`, `description` |
| Wide-format items | `item_1`, `item_2`, ... or `product_1`, ... (with or without the underscore) |
| Optional | `product_id` / `sku` / `item_id` / `stock_code`, `category` / `product_category` / `department`, `quantity` / `qty` / `units`, `unit_price` / `price`, `transaction_date` / `date` / `order_date` / `invoice_date`, `customer_id` / `customer` |

The UCI Online Retail headers (`InvoiceNo`, `StockCode`, `Description`, `Quantity`, `InvoiceDate`, `UnitPrice`, `CustomerID`, `Country`) are recognised; `Country` is ignored. Any other columns are ignored, and a warning lists them.

Values treated as missing (in IDs and product names): an empty cell, `nan`, `none`, `null`, `n/a`, `na`, `-`, `#N/A` and `?` (in any capitalisation).

## Cleaned data (`cleaned_transactions.csv` export)

- There is one row per product per transaction, with the recognised columns above.
- Product names are trimmed, their internal spaces collapsed, and stored in one Unicode form (NFC), so "Café" typed in two different ways is one product.
- Names that differ only in capitalisation are merged. The most common spelling wins; ties go to Title Case.
- Rows with a **negative quantity** are returns or cancellations. They are removed (see below), so a returned product is never counted as a purchase. A zero or unreadable quantity is left empty and the row is kept.
- Duplicate lines for the same product in one transaction are merged into one row, with their quantities added: each line is treated as a separate scan. Rules only use whether a product is in the basket, so they are not affected.
- Each product gets one category: its most common non-blank category. A blank category never outvotes a real one; products with no category become `Uncategorised`.
- `transaction_date` is stored as `yyyy-mm-dd`. Input may be ISO (`2025-01-05`), day/month/year or month/day/year with `/`, `-` or `.` separators, with or without a time. The order of day and month is decided once per file: a first number above 12 means day/month/year, a second number above 12 means month/day/year, and if every date could be either, day/month/year is used and a warning says so. Unreadable dates are left empty, with a warning. The date summary and the weekly chart use these stored dates.

## Removed rows (`removed_rows.csv` export)

| Column | Description |
|---|---|
| `file_row` | Line number in the uploaded file (the header is line 1) |
| `transaction_id`, `product_name` | Values as found, after trimming |
| `reason` | `missing transaction ID`, `blank product name`, `return or cancellation (negative quantity)`, `transaction has no products` or `duplicate product in the same transaction (merged)` |

## Rules (`rules.csv` export)

| Column | Meaning |
|---|---|
| `antecedents` | Products already in the basket (A) |
| `consequents` | Product(s) often also bought (B) |
| `antecedent support`, `consequent support` | support(A), support(B) |
| `support` | support(A ∪ B): share of all transactions containing every product in the rule |
| `confidence` | support(A ∪ B) / support(A) |
| `lift` | confidence / support(B) |
| `leverage` | support(A ∪ B) − support(A) × support(B) |
| `conviction` | (1 − support(B)) / (1 − confidence); infinite when confidence is 1 |

## Bundles (`bundle_opportunities.csv` export)

| Column | Meaning |
|---|---|
| `products`, `size` | Product set (2 or 3 products) |
| `transactions together` | Transactions containing the whole set |
| `support` | Share of transactions containing the whole set |
| `all-confidence` | support(set) / largest single-product support in the set |
| `lift vs independence` | support(set) / product of the single supports |
| `categories`, `potential use` | Category mix and a suggested use: shelve together within one category, or a cross-category display or bundle offer |

Only sets whose `lift vs independence` is above 1 and at least the minimum lift setting are listed (sets bought together less often than chance are never offered), and sets containing an ignored product are left out. The listed sets are ranked by `all-confidence`.

## Evaluation (`evaluation_summary.csv`, `evaluation_per_split.csv`)

| Column | Meaning |
|---|---|
| `cases` | Hidden-product cases per test split (average across splits in the summary) |
| `hit rate@3`, `hit rate@5` | Share of cases where the hidden product was in the top 3 / top 5 suggestions |
| `availability` | Share of cases with at least one suggestion |
| `coverage` | Share of training products (other than ignored products) that the method recommended at least once |
| `hit rate@k std` | Standard deviation across splits |
| `splits beating baseline@k` | Number of splits in which the method's hit rate was above the best-seller baseline |

## Real-world dataset: UCI Online Retail (not stored in this repository)

Chen, D. (2015). *Online Retail* [Dataset]. UCI Machine Learning Repository. <https://doi.org/10.24432/C5BW33>. Licensed under [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/legalcode). UCI describes it as all transactions between 1 December 2010 and 9 December 2011 of a UK-based, non-store online retailer that mainly sells all-occasion gifts; many of its customers are wholesalers.

`python scripts/download_uci_online_retail.py` downloads the official ZIP into `Data/external/uci_online_retail/` (ignored by Git) and writes:
- `online_retail.zip` — the official download, kept so the script never downloads it twice (`--force` downloads it again)
- `Online Retail.xlsx` — the spreadsheet inside the ZIP
- `online_retail.csv` — the same eight columns as UTF-8 text; spreadsheet dates are written as `yyyy-mm-dd hh:mm:ss` (they are real dates in the spreadsheet, so no day/month guessing is involved), whole numbers without a decimal part, and empty cells as empty fields
- `download_manifest.json` — source page, download URL, DOI, citation, licence, retrieval time (UTC), and the size and SHA-256 of each file

| Column | Meaning (from the UCI page) | How BasketWise uses it |
|---|---|---|
| `InvoiceNo` | Six-digit invoice number; a leading `C` marks a cancellation | Basket ID. `C…` invoices and other letter-prefixed invoices (`A…`, bad-debt adjustments) are removed |
| `StockCode` | Product code | Product ID, trimmed and in upper case (`85123a` and `85123A` are one product). Service and accounting codes are removed: `POST`, `DOT`, `C2`, `23444` (postage and carriage), `M` (manual), `D` (discount), `S` (samples), `B` (bad debt), `BANK CHARGES`, `AMAZONFEE`, `CRUK`, and `GIFT_0001_*` vouchers |
| `Description` | Product name | Display name only: the most frequent description of each stock code. Labels add the code, such as `WHITE HANGING HEART T-LIGHT HOLDER (85123A)`, because some descriptions belong to several codes |
| `Quantity` | Units per line | Zero or negative quantities are removed (returns and stock adjustments). Repeated lines of a product in one invoice are merged and their quantities added |
| `InvoiceDate` | Date and time of the invoice | Must be an ISO date-time; anything else is removed as an invalid date. An invoice's time is its earliest line |
| `UnitPrice` | Price per unit in sterling | Missing, zero or negative prices are removed |
| `CustomerID` | Five-digit customer number | Kept when missing (a basket is an invoice); `--require-customer-id` drops such rows instead |
| `Country` | Customer's country | Reported in the data-quality summary only |

### Real-world validation outputs (`outputs/real_world/`)

| File | Contents |
|---|---|
| `data_quality_report.json` | Counts measured on the raw table: missing values, duplicates, cancellations, negative quantities, invalid dates and prices, codes and descriptions, customers, countries, invoices per month |
| `preprocessing_summary.csv` | `step`, `count`: original rows, rows removed for each reason, valid purchase rows, duplicates and merges, basket lines, invoices, products and customers |
| `removed_rows.csv.gz` | Every removed raw row (`file_row` is its line number in the CSV) with the first reason that applies. Customer IDs are not included |
| `real_world_evaluation.json` | Source, provenance (SHA-256 of the file used), preprocessing, split, settings, threshold selection, metrics per method with 95 % intervals, weekly results, limitations and software versions |
| `real_world_evaluation.md` | The human-readable report generated from the same results |
| `evaluation_summary.csv` | One row per method: `cases`, `invoices`, `customers`, `hit rate@K`, `precision@K`, `recall@K`, `availability`, `coverage`, `invoice-averaged hit rate@K`, and the hit rate on cases whose hidden product was sold in training |
| `weekly_results.csv` | Hit Rate@K of every method per test week |
| `threshold_selection.csv` | Each candidate setting with its rule count and validation scores, and which one was chosen |
| `training_rules.csv` | Every rule learned from the training period, with product labels |
| `evaluation_cases.csv.gz` | One row per leave-one-out case: invoice, time, hidden product, whether it was sold in training, and for each method the rank of the hidden product in the top K (0 = not found) and how many products were suggested |
